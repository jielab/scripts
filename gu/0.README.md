### gu.sh — detailed reference

```text
./gu.sh phyml --loci /mnt/f/gwas/main/common/bald0/gwas/bald0.jma.cojo --loci-format cojo --grch 38 --target 1kg --dir-target /mnt/f/gen/1kg/37/pfile/chr --jobs 1 --memory-cap 32G

# UKB：PSAM 前 10000 人，再筛男性；默认 chr1–22、X。
./gu.sh ibdmix-GPU --grch 37 --target ukb --dir-target /mnt/f/gen/ukb/37/imp/chr --dir-out /mnt/f/analysis/gu/ukb --postfix 001 --keep-psam /mnt/f/gen/ukb/37/imp/chr1.psam,10000,1 --keep-males

# --dir-target 是染色体文件前缀；--dir-out 与 --postfix 拼成 /mnt/f/analysis/gu/ukb001。
# CPU/GPU 输出分别在 ukb001/ibdmix/ 和 ukb001/ibdmix-GPU/。
# --keep-psam FILE,每批人数,批次号（从 1 开始）；--keep-males 在分批后筛男性。
# 可追加 --chr 22 或 --chr 1,2,X；默认五个参考 Altai,Chagyr,Denisova,Denisova25,Vindija。
# 追加 --archaic-gen Altai,Denisova 可仅使用这两个参考；也可从上述五个中任选一个或多个，以逗号分隔，替换默认列表。
# ibdmix-GPU 默认 --jobs 4 --memory-cap 16G --replace-ibdmix FALSE --foreground TRUE --auto-final FALSE。
# IBDmix-GPU 并行准备染色体，GPU 调用按设备串行，避免显存叠加。

./gu.sh trace --chr 22 --grch 37 --dir-arg /mnt/f/gen/1kg/37/arg.threads/trees --target 1kg --dir-target /mnt/f/gen/1kg/37/pfile/chr --jobs 1 --memory-cap 32G
./gu.sh as3 --chr 22 --grch 38 --target 1kg --dir-target /mnt/f/gen/1kg/38/pfile/chr --jobs 1 --memory-cap 32G

# UKB 运行完成后：GPU 汇总/查看。
GU_RESULT_MODULE=ibdmix-GPU ./gu.sh final --dir-out /mnt/f/analysis/gu/ukb --postfix 001
GU_RESULT_MODULE=ibdmix-GPU ./gu.sh shiny --dir-out /mnt/f/analysis/gu/ukb --postfix 001

```

<a id="overview--project-output-conventions"></a>

### Project output conventions

- GU 的个体／单倍型及原生拟合结果按方法、数据集和位点／染色体保存为 `phyml.haplotypes.rds`、`ibdmix.tracts.rds`、`trace.segments.rds` 或 `as3.tracts.rds`；综合个体结果保存为 `final/gu.results.rds`。SQLite 仅作为 `/tmp` 中的查看缓存；`gu.validation.rds` 保留需供 Shiny 读取的个体验证数据。正式结果不重复复制到 `final/normalize`。

临时空间清理：IBDmix 成功完成后删除已保存 QC 的掩膜缓存；GU 调度的整批分析成功后，
清理该结果目录对应的 `/tmp/gu-ukb-prepared`、`gu-intermediate` 和 `gu-native-view`。
仍被其他进程引用的结果范围、未识别的目录和正式结果不会删除。设置 `GU_KEEP_SCRATCH=1`
可保留成功运行的缓存。手工检查可用 `python3 f/cleanup.py`，确认执行加 `--apply`；
加 `--work /mnt/f/analysis/gu/ukb001` 可限定结果范围。删除后的读取副本会从结果归档重建，
VCF 准备缓存会从原始基因型重新生成。清理失败只发出警告，不把已完成分析标为失败。

### ukb_prepare.sh — subcommand reference 2

```text
Usage:
  bash f/ukb_prepare.sh ancestral --in target.vcf.gz --ref 1kg.chrN.vcf.gz --out out.vcf.gz [--threads N]

The reference VCF must contain INFO/AA. INFO/AA values such as A||| are normalized to
```

## GU 内部模块

日常分析从上一级的 `gu.sh`、`arg.sh` 启动。此目录按功能组织内部实现。

| 文件 | 用途 |
| --- | --- |
| `ukb_prepare.py` | UKB PGEN 检查、样本选择、固定队列、VCF 导出及质控、古人类评分输入准备 |
| `0.common.py progress` | 旁路观察 UKB 子进程与文件读取进度，报告当前读取的预计剩余时间，不改动准备缓存身份 |
| `ukb_prepare.sh` | UKB 原始 BGEN/芯片输入检查、VCF 导出和祖先等位基因注释；PGEN 操作交给同名 Python 模块 |
| `gwas_loci_prepare.py` | COJO 信号归并、基因组坐标转换、GRCh37 区间及审计表生成 |
| `introgression_review.py` | 渗入证据复核、原始 lead 与单倍型标签比较、HTML/TSV 报告 |
| `results_normalize.py` | 整合各方法结果到 SQLite、参考结果缓存和渗入密度汇总 |
| `arg.sh` / `arg.py` | ARG 内部工作流及数据转换、缓存工具；入口为上一级 `arg.sh` |
| `arg.py singer` / `arg.py threads` | SINGER、Threads 各自的 ARG 后端 |
| `ibdmix.sh` / `ibdmix.py` | IBDmix 调度、掩膜、群体样本、质控和片段汇总 |
| `ibdmix.py loci` | Shiny 的群体窗口支持峰汇总，保留人数分母与去重规则 |
| `ibdmix.py resume` | UKB 整染色体续跑：预处理前核验原始输入、样本内容、调用参数与结果完整性；临时样本文件重建不使已完成结果失效 |
| `ibdmix.prepare.cc` / `ibdmix.sh build-prepare` | 共享 HTSlib 预处理器及编译入口，一次读取现代基因型供多个古人类参考使用 |
| `ibdmix.gpu.cu` / `ibdmix.sh build-gpu` | IBDmix CUDA 片段调用器及编译入口 |
| `phyml.py` / `phyml.R` | PhyML 分析、结果检查及绘图 |
| `trace.sh` / `trace.py` | TRACE 分析及片段处理 |
| `as3.sh` / `as3.py` | ArchaicSeeker 3 分析及输入、结果处理 |
| `0.common.py` / `0.common.sh` / `0.common.R` | 跨方法共享的坐标、样本、路径、缓存和结果归档工具 |

UKB 的 Shell 和 Python 模块分别承担原始 BGEN/芯片与 PGEN 准备，保持独立以避免把两套输入流程混在一起。独立的位点准备、证据复核和结果整合也保留各自入口；重复的空命令分发层和模块加载已去除。

IBDmix 原生辅助文件直接平铺在 `f/`，使用 `ibdmix.` 前缀。构建与运行说明见 [ibdmix.md](#doc-f-ibdmix)，许可证见 [ibdmix.LICENSE](f/ibdmix.LICENSE)。已安装的可执行文件仍位于软件目录。

IBDmix 默认 `--replace-ibdmix FALSE` 时，UKB 整染色体任务先检查历史结果。完整且兼容的结果打印 `[GU CMD] SKIP`；部分完成的结果继续补跑。历史归档中的原始输入记录会保存为结果目录内的 `.ibdmix.resume.json`，用于避免重新预处理覆盖旧质控记录后丢失续跑依据。样本选择按实际队列及顺序校验，原始 PGEN、参考基因组、古人类 VCF、掩膜和计算参数仍参与检查；不兼容时在预处理前报明原因。该检查不改写旧调用或最终片段。

IBDmix 掩膜的旧文件 SHA 保留为审计证据；只有此次整合前的确切版本、且掩膜函数与常量的语法树一致时，续跑才接受旧记录。输入、样本、参数和片段校验仍按原规则执行。新掩膜记录当前代码的真实 SHA。

## Bundled ArchaicSeeker3 source

This directory contains the minimal runtime source copied from the official
`Shuhua-Group/ArchaicSeeker3.0` GitHub `main` archive downloaded on 2026-08-27.
GU intentionally keeps the model checkpoints outside the scripts tree under
`/mnt/f/gen/archaic/38/models`.

Install through `gu/install.sh`: non-Torch dependencies are maintained in
`requirements-gu.txt`, and the installer selects the GPU-specific Torch profile.
The unused upstream dependency list is not bundled.

The training and inference module is named `src/stepsagnostic/training_inference.py`;
package exports and installer checks use this name. Unused ResUNet source files
were removed; the active Mamba/Transformer and smoother definitions are unchanged.

Two runtime-only compatibility edits are applied locally:

- NumPy 2 scalar conversion uses the first element of the one-element ancestry array.
- Pandas Copy-on-Write uses assignment instead of chained `fillna(..., inplace=True)`.

Upstream: <https://github.com/Shuhua-Group/ArchaicSeeker3.0>

Local source cleanup (2026-09-13): removed earlier, unconditionally overwritten
definitions of `find_introgression_segments` (3),
`inference_and_save_basemodel_overlap` (2), and `SmootherDataset` (1).
The final definitions, signatures, defaults and bodies are unchanged.

### About

`ArchaicSeeker3.1-mamba` is an algorithm for detecting archaic introgression segments (e.g., from Neanderthals and Denisovans) in modern human genomes. It is based on the Mamba (SSM-Mamba) architecture, designed for accurate and efficient analysis of large-scale genomic data.

This repository provides the core software and example scripts to demonstrate how to use it for parallel analysis on multi-GPU systems.

<a id="doc-f-as3-upstream-readme--direct-downloads-from-the-as3-web-service"></a>

#### Direct downloads from the AS3 web service

The following GRCh38 data are available as public, read-only static downloads and can be used directly without an AS3 web account:

<a id="doc-f-as3-upstream-readme--ref1028-reference-panel"></a>

##### Ref1028 reference panel

**[Browse the Ref1028 release](https://pog.fudan.edu.cn/as3-downloads/reference-panel/Ref1028/)**

This is the exact chromosome-wise panel currently configured in the AS3 web service. For chromosome `N`, download all of the following:

```text
Ref_Panel.chrN.vcf.gz
Ref_Panel.chrN.vcf.gz.tbi
Ref_Panel.map.txt
```

Example for chromosome 22:

```bash
wget https://pog.fudan.edu.cn/as3-downloads/reference-panel/Ref1028/Ref_Panel.chr22.vcf.gz
wget https://pog.fudan.edu.cn/as3-downloads/reference-panel/Ref1028/Ref_Panel.chr22.vcf.gz.tbi
wget https://pog.fudan.edu.cn/as3-downloads/reference-panel/Ref1028/Ref_Panel.map.txt
```

The VCF can be supplied directly to `--reference`, and `Ref_Panel.map.txt` can be supplied directly to `--map`.

The panel contains four high-coverage archaic genomes—`AltaiNeandertal`,
`Vindija33.19`, `Chagyrskaya-Phalanx`, and `Denisova`—together with the modern
human reference samples used by AS3.

After downloading the chromosome-specific panel and map into the current
directory, the only analysis input that users need to supply is their phased
target VCF. For example, for chromosome 22:

```bash
TARGET_VCF=/path/to/input.phased.chr22.vcf.gz
CUDA_VISIBLE_DEVICES=0 python ArchaicSeeker3.1-mamba \
  -t "${TARGET_VCF}" \
  -r Ref_Panel.chr22.vcf.gz \
  -m Ref_Panel.map.txt \
  -o as3_chr22
```

<a id="doc-f-as3-upstream-readme--grch38-3n1d-high-quality-region-masks"></a>

##### GRCh38 3N1D high-quality-region masks

**[Browse the GRCh38 3N1D mask release](https://pog.fudan.edu.cn/as3-downloads/high-quality-mask/GRCh38/3N1D/)**

The source FilterBeds for three high-coverage Neanderthal genomes (Altai, Vindija33.19 and Chagyrskaya) and one Denisovan genome were lifted from hg19 to GRCh38. For each chromosome, the four lifted BEDs were concatenated, coordinate-sorted and combined with `bedtools merge`; these files therefore represent the merged union of the four source pass-interval sets.

Two equivalent chromosome naming styles are provided:

```text
chrN_mask.bed       # chromosome column: 1, 2, ...
chrN_mask.wchr.bed  # chromosome column: chr1, chr2, ...
```

Choose the file matching the chromosome convention in your VCF. The mask is directly usable by interval-aware tools, for example:

```bash
bcftools view -T chr22_mask.wchr.bed -Oz -o input.high_quality.vcf.gz input.vcf.gz
```

The bundled `00.preprocess.sh` example currently expects separate `N_chrN.bed` and `D_chrN.bed` files. To use the combined 3N1D release, apply the BED directly as above or adapt that mask stage to use one combined file.

These masks are intended for users building or filtering a custom reference
panel. They are not required when using the downloadable preprocessed Ref1028
panel.

Each release directory contains a `README.txt` and `SHA256SUMS`. Static downloads support HTTP range requests, so interrupted downloads can be resumed.

<a id="doc-f-as3-upstream-readme--usage-workflow"></a>

### Usage Workflow

The recommended path is to use the downloadable Ref1028 VCF and map directly,
as in the chromosome 22 quick-start command above. No reference-panel
preprocessing is required.

Use `00.preprocess.sh` only when building a custom reference panel. Configure
all paths in its **User Configuration** section before running it; the repository
does not bundle the placeholder `examples/raw_data` files. The script produces
`Final_Target_VCFs`, `Final_Ref_VCFs`, and `reference.map`.

For a configured multi-chromosome dataset, `01.run_archaicseeker3.sh` provides
parallel GPU execution. Set its input/output paths and GPU list, then run:

```bash
bash 01.run_archaicseeker3.sh
```

<a id="doc-f-as3-upstream-readme--run-a-single-chromosome-directly"></a>

#### Run a Single Chromosome Directly

To analyze a single chromosome without the multi-chromosome wrapper script,
run ArchaicSeeker3 directly:

**Basic Command:**
```bash
CUDA_VISIBLE_DEVICES=0 python ArchaicSeeker3.1-mamba \
    -t <path/to/target.vcf.gz> \
    -r <path/to/reference.vcf.gz> \
    -m <path/to/map.txt> \
    -o <path/to/output_folder> \
    [OPTIONS]
```

**Command-Line Arguments:**

| Argument | Shorthand | Description | Default |
| :--- | :--- | :--- | :--- |
| **`--test-mixed`** | `-t` | **Required.** Path to the phased VCF file of the target samples. | `None` |
| **`--reference`** | `-r` | **Required.** Path to the reference panel VCF file (archaic & African). | `None` |
| **`--map`** | `-m` | **Required.** Path to the reference map file. | `None` |

<a id="doc-f-as3-upstream-readme--output-format"></a>

### Output Format

AS3 now performs its standard BED construction internally. The default command:

1. retains raw segments with length `>= 5 kb` and score `>= 0`;
2. exact-merges retained segments with the `--merge` distance (default `10 kb`);
3. recalculates ancestry label, SNP counts, and mean score from the raw SNP details;
4. writes the combined result and ancestry-specific BED files.

The raw BED is filtered in bounded pandas chunks. Exact merge then scans the
gzip SNP-detail table once and immediately reduces retained rows into numeric
merge-group totals; it does not materialize the full SNP table or keep per-row
NumPy arrays. Later target-sample chunks are stored as concatenated gzip members
instead of repeatedly decompressing and rewriting earlier chunks. These changes
preserve the exact-merge rules while bounding post-processing memory.

The standard output files are:

```text
introgression.bed
introgression.denisovan.bed
introgression.neanderthal.bed
introgression.mosaic.bed
introgression.raw.bed
introgression.raw.snps.gz
introgression_prediction.txt
run.log
```

<a id="doc-f-as3-upstream-readme--1-introgressionbed"></a>

#### 1. `introgression.bed`

This is the canonical combined result after the standard 5 kb pre-filter and
exact merge. The three ancestry-specific BEDs use the same format and contain
only the corresponding rows.

| Column | Description |
| :--- | :--- |
| **Chr** | Chromosome |
| **Start** | First supporting VCF `POS` value (1-based, inclusive) |
| **End** | Last supporting VCF `POS` value (1-based, inclusive) |
| **Haplotype** | Internal numeric haplotype index used during inference. |
| **Archaic** | Predicted source: `1`=Denisovan, `2`=Neanderthal, `3`=Mosaic |
| **#SNP** | Number of SNPs within the segment |
| **Score** | Mean score recalculated from the SNPs supporting the final merged label. A higher score indicates higher confidence. |
| **#SNP_Archaic1** | Number of SNPs supporting Archaic Source 1 |
| **#SNP_Archaic2** | Number of SNPs supporting Archaic Source 2 |
| **SampleID_HapID** | A globally unique identifier combining the original Sample ID and haplotype (1 or 2). |

Although these files use a `.bed` suffix, AS3 preserves the 1-based VCF SNP
positions rather than converting them to standard 0-based, half-open BED
coordinates. AS3 length thresholds are evaluated as `End - Start`.

<a id="doc-f-as3-upstream-readme--2-raw-and-snp-level-outputs"></a>

#### 2. Raw and SNP-level outputs

`introgression.raw.bed` preserves the unmerged segment calls, and
`introgression.raw.snps.gz` preserves the SNP-level evidence used for exact
merge and custom reprocessing. These files are not overwritten by the standard
post-processing step.

`introgression_prediction.txt` provides the SNP-level ancestry matrix:

-   **Rows**: Haplotype indices.
-   **Columns**: Variant positions.
-   **Values**: Predicted ancestry: `0`=African (non-introgressed), `1`=Denisovan, `2`=Neanderthal.

## IBDmix native helpers

<a id="doc-f-ibdmix--cuda-caller"></a>

### CUDA caller

`/mnt/d/scripts/gu/gu.sh ibdmix-GPU` uses a local CUDA implementation of the
IBDmix segment stack. This is an experimental GU backend, not an upstream GPU
release. It was derived from PrincetonUniversity/IBDmix commit
`6a9d4bc67dcaf602e65cac0fa6191e1e7a1291ef` and is GPL-3.0 licensed (see [ibdmix.LICENSE](f/ibdmix.LICENSE)).
Upstream: https://github.com/PrincetonUniversity/IBDmix

The calling unit is a modern **individual's genotype**, compared with one archaic
individual. Autosomal phased haplotypes are not called separately. The selected
modern cohort supplies allele frequencies. Male non-PAR X is converted using the
existing GU X contract and independent non-PAR components are called separately.

CPU and GPU entry points default to exactly
`Altai,Chagyr,Denisova,Denisova25,Vindija`. New calls reject `.2013` references;
historical replication files remain readable.

<a id="doc-f-ibdmix--run"></a>

### Run

```bash
cd /mnt/d/scripts/gu
bash f/ibdmix.sh build-gpu

./gu.sh ibdmix-GPU --grch 37 --target ukb \
  --dir-target /mnt/f/gen/ukb/37/imp/chr \
  --dir-out /mnt/f/analysis/gu/ukb --postfix 003 \
  --keep-psam /mnt/f/gen/ukb/37/imp/chr1.psam,2000,3 --keep-males \
  --archaic-gen Altai,Chagyr,Denisova,Denisova25,Vindija
```

This example writes to `/mnt/f/analysis/gu/ukb003/ibdmix-GPU/<unit>/`.
The default 1KG destination is `/mnt/f/analysis/gu/1kg/ibdmix-GPU/<unit>/`.
`--dir-out` selects the shared result root; each module uses its exact CLI name
for the next directory, command lists and logs. GPU runs default to `--jobs 4`
chromosome workers, subject to the RAM budget. At the default `--memory-cap 16G`,
each UKB worker receives a 1024 MiB PLINK workspace, with 2048 MiB per worker
and 4096 MiB shared overhead reserved. An explicit `GU_PREP_MEMORY_MB` is honored
and can reduce concurrency. `--jobs 1` restores serial chromosome processing.
Preparation can overlap across chromosomes; CUDA calls share a per-user,
per-device lock and run one at a time to avoid adding their peak VRAM usage.
The lock coordinates GU IBDmix callers, not unrelated GPU programs. Each
chromosome still uses one population worker. Results retain method `ibdmix`; their
provenance records `cuda-segment-v1`, a distinct pipeline version and the
binary SHA-256. For a summary using these GPU calls, run
`GU_RESULT_MODULE=ibdmix-GPU ./gu.sh final --dir-out /mnt/f/analysis/gu/ukb003`.
It writes to `ukb003/final/ibdmix-GPU/`; use the same environment variable with
`./gu.sh shiny` to view it. CPU runs use `ukb003/ibdmix/` and `ukb003/final/`.

<a id="doc-f-ibdmix--what-is-accelerated"></a>

### What is accelerated

The GPU maintains a separate streaming segment stack for every selected modern
individual, accumulates LOD scores in double precision and emits the original
region statistics. The CPU computes population frequencies and the three
possible genotype LODs per site using the original upstream formulas. It also
handles parsing, masks, VCF conversion, compression, QC and final filtering.
Do not interpret caller speedups as whole-pipeline speedups.

Genotype preparation now uses the [shared HTSlib reader](#doc-f-ibdmix--shared-genotype-preparation):
one modern genotype pass supplies all five references, with QC during emission.
CPU/GPU callers receive the same canonical genotype text as before. Progress on
screen is limited to preparation and reference/chromosome completion; detailed
diagnostics are retained in log files.

UKB preparation also reports the current process, elapsed time and input file
offset every 30 seconds, including an estimate for the current read when it is
advancing. A file offset is not whole-chromosome completion: VCF export, audit,
shared genotype preparation and reference calls follow the PGEN subset pass.
The monitor is separate from the preparation implementation so adding progress
does not invalidate its scientific cache receipts. Already-running schedulers
keep their original concurrency; these defaults apply on the next launch.

Site batches preserve all pending stacks, so a batch boundary does not create
a segment boundary or change frequencies. Candidate storage grows before each
batch by appending pages of up to 2048 nodes per individual. Existing pages
remain allocated in place; growth neither copies the complete stack nor doubles
its capacity. Only the pages required for the next batch are added. This avoids
the old simultaneous allocation of a full old and new stack, which could fail
even when the live stack would fit in VRAM.
Growth is bounded by available VRAM and `IBDMIX_GPU_MAX_NODES`. Exceeding
the limit produces an explicit failure, never a truncated successful result
or a silent CPU fallback. Output order matches upstream's site/sample order.

<a id="doc-f-ibdmix--configuration-and-limitations"></a>

### Configuration and limitations

The local build uses CUDA 12.8 from the existing `as3_mamba` environment and
`-arch=native`; rebuild on a different GPU. The caller itself is a native binary
and does not require PyTorch. Build overrides: `IBDMIX_NVCC`, `IBDMIX_RUNTIME`
(upstream source checkout), `IBDMIX_GPU_BIN` (output executable).

Runtime overrides, also recorded in generated chromosome commands:

| Environment variable | Default | Meaning |
| --- | --- | --- |
| `IBDMIX_GPU_DEVICE` | 0 | CUDA device ordinal |
| `IBDMIX_GPU_BATCH_SITES` | 2048 | Sites transferred per batch |
| `IBDMIX_GPU_NODES` | 2048 | Initial candidate nodes per individual |
| `IBDMIX_GPU_MAX_NODES` | 131072 | Upper bound for candidate nodes per individual |
| `IBDMIX_GPU_EVENTS` | 1048576 | Maximum emitted segments per batch |

The caller accepts one chromosome, canonical `generate_gt` input and the flags
used by GU, including sample selection, masks, error rates, MAC, LOD, inclusive
ends and `--more-stats`. It does not implement upstream `--write-snps` or
`--write-lods`; unsupported options fail explicitly. It rejects malformed
records, duplicate selected sample IDs, selection of the archaic as a modern
sample and unsorted positions.

VRAM consumption grows with cohort size and the longest retained candidate
stack. A test with 917 individuals is not validation for all approximately
500,000 UKB participants at once. Do not split a cohort into independent
frequency-estimation batches solely to fit GPU memory: that changes the model.
Use the original CPU entry point if a fixed cohort exceeds available memory.
`--memory-cap` controls system RAM, not GPU VRAM. Other GPU workloads also reduce
the VRAM available to this caller. Caller failures now include the reference,
population, exit status, detailed log path and the final error lines in the
main run log.

Rebuilding changes the GPU binary SHA-256 recorded in result provenance.
Existing results remain readable, but cannot be resumed with a different binary.
Use a new output postfix to retain the existing run when rerunning a full genome
with a rebuilt caller. `--replace-ibdmix TRUE` explicitly discards and recomputes
the selected existing results.

<a id="doc-f-ibdmix--local-measurements-2026-10-11"></a>

### Local measurements, 2026-10-11

On the RTX 5090 Laptop GPU, 917 UKB individuals and the prepared Altai chr22
genotypes (746,710 sites) produced 68,502 raw segments, byte-identical to the
original caller in all three runs. CPU wall times were 28.21, 43.69 and 31.12 s;
GPU wall times were 13.56, 13.80 and 14.53 s. The median caller speedup was 2.26x.
These real-data timing runs used no exclusion mask; masks were exercised in
the synthetic equivalence and five-reference pipeline tests.

A male chrX region at X:10,000,000–12,000,000 also produced byte-identical output
(2,392 segments). That small input took 0.72 s on CPU and 0.81 s on GPU in one
run; GPU startup and transfer costs can outweigh benefits for small inputs.
This is not a whole-UKB or whole-chrX validation.

The paged-memory correction was also verified against the failing full chr3
Denisova call with the same 4,564 individuals and excluded-site mask. It completed
all 4,233,154 sites in 235.808 seconds of caller time, producing 1,071,267 raw
segments. The maximum stack held 83,968 nodes per individual (11.421 GiB of node
storage); the previous 65,536-to-131,072 reallocation would require 26.742 GiB
of simultaneous old and new node storage. This real-data check verifies completion;
CPU equivalence was tested separately in 28 synthetic comparisons and the
five-reference pipeline. Historical reports/logs were removed from the source tree.

<a id="doc-f-ibdmix--shared-genotype-preparation"></a>

### Shared genotype preparation

`f/ibdmix.sh` automatically builds and uses `ibdmix.prepare.cc` for CPU and CUDA runs.
HTSlib reads the modern VCF once per analysis unit; decoded genotypes are shared
by all missing archaic references. It reads VCF/BCF directly, avoiding the previous
`bcftools → text VCF → generate_gt` pipeline for every reference. All compressors
share four threads by default (`IBDMIX_PREPARE_THREADS`).

The merge follows upstream `generate_gt`: modern indels remain merge barriers,
archaic homozygous-reference records remain informative at shared sites, and
archaic-only non-reference sites are emitted only before modern EOF. Missing
alleles, haploid duplication, allele matching, ordering, sample identity and
chrX non-PAR filtering retain the existing contract. QC is accumulated while
writing, avoiding a second full genotype decompression. Files become reusable
only after all readers and compressors succeed.

Genotype outputs remain gzip-compatible text. Up to five compressed inputs are
kept under `/tmp` and removed after their calls; no large uncompressed modern VCF
is cached. Completed reference calls can still be resumed independently. The
pipeline version and preparation binary SHA-256 participate in provenance.

Build explicitly with `bash f/ibdmix.sh build-prepare`. The build uses the GU
Conda environment's HTSlib, with overrides `IBDMIX_HTSLIB_PREFIX`, `CXX`, and
`IBDMIX_PREPARE_BIN`. Production runs rebuild only when sources change.

### Logs

completion/reuse and failure summaries. Full diagnostics remain in the main log;
the native preparer's diagnostics are in `logs/<unit>.prepare.log`.

## Experimental PhyML CUDA backend

`./gu.sh phyml-GPU` runs the original PhyML tree search and model optimization
with a CUDA nucleotide pruning kernel. This is a local experimental build, not
an official GPU release. Source: https://github.com/stephaneguindon/phyml at
`42bb4b52f479938a3427dfe4357b861f0e306686` (3.3.20260528, GPL-3.0).

The adapter changes the partial-likelihood update in `src/lk.c`; the CUDA kernel
evaluates sites and rate categories using double precision without fused
multiply-add. Tip ambiguities, all-missing subtrees, zero-weight bootstrap
patterns and the original powers-of-two scaling are preserved. Branch/model
optimization, topology search, likelihood reductions and bootstrap sampling
remain the upstream CPU implementation. GU's VCF/LD/haplotype preparation also
remains CPU. The GU model is still HKY85+G4+I with 100 bootstrap replicates.

Build using the existing CUDA 12.8 installation:

```bash
bash f/phyml_gpu/build.sh
```

The original installed `phyml` and `phyml-mpi` binaries are not replaced.
The build is installed under `/mnt/d/software/gu/phyml-gpu`, with a source/binary
SHA-256 manifest. A dedicated source checkout is used. `PHYML_GPU_BIN` and
`PHYML_GPU_DEVICE` select binary/device. `PHYML_TREE_SEED` is propagated to both
CPU and GPU workers; the recorded comparisons used 42 and one worker.
GPU outputs use `<result-root>/phyml-GPU/<unit>/`, defaulting to
`/mnt/f/analysis/gu/1kg/phyml-GPU/`. Command lists and logs also use `phyml-GPU`.
Use `GU_RESULT_MODULE=phyml-GPU ./gu.sh final --dir-out <result-root>` to write
the corresponding summary under `<result-root>/final/phyml-GPU/`.
No CPU fallback is used for
missing CUDA, allocation errors, or unsupported models/scaling.

**This first implementation is slower on the tested small trees.** Host/device
transfers occur for each partial update. An 8-tip, 120-site synthetic alignment
took 0.09 s on CPU and 4.74 s on GPU; a 62-tip, 450-site 1KG-derived alignment
took 2.87 s and 131.92 s respectively (one run each, no bootstrap). These are
observations, not expected UKB speedups. GPU utilization alone is not evidence
of useful acceleration. Keeping likelihood buffers resident on the device and
batching tree operations would be a separate optimization effort.

Historical kernel validation covered 48 tip/internal, ambiguity, category, scaling and batch
size combinations. Historical tree comparisons also checked log likelihood,
unrooted splits, branch lengths, bootstrap counts and supports. Floating-point
changes can affect optimization/search, so byte equality is not a universal
guarantee. Historical benchmark scripts and reports were archived during cleanup.

<a id="doc-f-trace-gpu-readme--shared-cpugpu-numerical-correction"></a>

### Shared CPU/GPU numerical correction

The installed upstream initialization calls
`gamma_sp.pdf(subncoal, self.emi2_a1, 1 / self.emi2_b1)`. SciPy interprets the
third positional argument as `loc`, not `scale`. On the real 1KG test this made
all cached null emissions infinite and all fitted posteriors NaN.

Both `gu.sh trace` and `gu.sh trace-GPU` now run through `../trace.py infer`,
which applies exactly the same one-line correction:
`gamma_sp.pdf(subncoal, a=self.emi2_a1, scale=1 / self.emi2_b1)`.
It is recorded as `gu-trace-gamma-scale-v1`. Old run metadata cannot silently
reuse results produced without this correction; use a new output directory or
explicit replacement. CPU/GPU comparisons should use separate output roots.
Inference outputs are checked for finite parameters, normalized finite
posteriors and valid ZIP data before being published.

Other upstream behavior, including forward/backward precision and masked-column
transition indexing, is preserved. The purpose of this backend is comparison
with the same TRACE model; it is not an independent validation of that model.

Historical validation compared kernels, complete fits, decoded posteriors and
classifications at 0.9. The comparisons also checked CLI NPZ outputs
and pipeline segment tables. Speed depends on tree/window
count and CPU extraction cost; a GPU name does not promise a faster full run.

On 2026-10-11, two haplotypes from the full 1KG chr22 THREADS ARG (88,734 trees)
had a maximum CPU/GPU posterior difference of 2.1e-25 and byte-identical final
summary tables. CLI inference times were CPU 3.32/3.17 s and GPU 3.38/3.03 s,
one run per haplotype, including startup and excluding ARG extraction. These
measurements show similar runtimes, not an established speedup. A separate
200 kb region pipeline produced nine identical normalized segment rows.
Historical benchmark scripts and reports were archived during cleanup.

- `phyml.R`、`dual_lead.R`：PhyML 报告与双 lead 面板。
- `ref.R`：IGV 本地参考序列服务。
- `review.R`：已有静态 review 页面的小型 Shiny 宿主。
- `www/`：JavaScript、CSS、地图数据和 IGV 静态资源。

五参考分析默认使用 Altai、Chagyr、Vindija、Denisova、Denisova25。
PhyML 在同一棵树上分别检验 Neanderthal（三参考）和 Denisovan（两参考），
报告、携带者验证和图像均按谱系分开。加入参考后需要重新建树；旧的三参考树不能充当 Denisovan 结果。

Overview 的 Locus evidence overview 仅显示报告中 `call=tree_supported` 的记录，
不按序列 QC 筛选；QC 状态仍显示。每行对应一个 locus 的一个支持谱系，
表上方同时列出独立 loci 数和谱系记录数。全部输入 loci 仍可在 PhyML → 全部位点和下载汇总中查看。

IBDmix 密度图上方的 Supported loci 表按群体窗口支持定义候选区间，不限 GWAS loci，
不再按 `segment_catalog` 中的原始片段边界分组列出。
它沿用 final 中保留的原生片段过滤、科学参考范围及已完成运行的 `evidence_eligible` 资格。
实验性 chrX、2013 对照参考及只能证明局部分析范围的运行不计入。

默认规则由 `f/ibdmix.py loci` 实现：

1. 按谱系、染色体和个体合并科学参考的重叠片段；每个人在同一碱基最多贡献一个支持拷贝。
   分母使用该谱系至少一个科学参考的完整常染色体运行中实际检测的个体并集，包括零片段个体。
   必须有保存的 caller roster；缺失时排除并提示，不能用阳性人数或注释面板推断。
2. 将染色体划为不重叠的 50 kb 窗口，计算
   `p(w) = Σ个体合并覆盖bp / (窗口bp × 2 × 实际检测人数)`。
   因 IBDmix 未分相，该指标是保守拷贝支持率，不能当作已知 haplotype 频率或渗入概率。
   短片段仅按实际覆盖长度贡献支持，跨参考重复命中不会增加支持率。
3. 每条染色体独立取相邻 3 窗口的中位数（边缘只用实际存在的邻居）。
   每个谱系的背景 `b = max(1%, 已检测常染色体的 Σ覆盖bp / Σ二倍体检测bp)`，
   包含已经检测但零片段的染色体，不外推未检测染色体。
4. 核心窗口必须同时满足原始及平滑支持率 `≥2b`，且至少连续 2 个完整窗口（100 kb）。
   从核心沿原始及平滑支持率均 `≥b` 的连续窗口扩展，合并为一行；
   低于背景的窗口立即切断，不能被平滑填补或跨染色体、跨谱系连接。
5. 按 `Σ max(平滑支持率-b,0) × 窗口长度kb` 降序排列，峰值用于打破并列。
   此面积在表格中标为“IBDmix 支持强度”，不是统计显著性，也不是跨方法独立证据的数量。
   所有通过规则的区间仍保留在计算结果和完整下载中；网页在谱系、染色体及最低峰值筛选后，
   按此强度取前 50 个，保留全局排名。默认从支持最强的位点开始展示。

例如 1,000 人中 10 人各有一个覆盖完整窗口的片段，支持率为 `10/2000=0.5%`，不能入选；
20 人对应 1% 背景下限，仍不足以建立 2% 核心峰。该门槛针对群体高支持区间，不能据此否定罕见个体片段。

The bundled coordinates let R draw the static map without a mapping package or

mean per-individual autosomal Neanderthal physical coverage. Benchmark Mb/person
values come from [Chen et al., Cell 2020, Fig. 2A / Table S4](https://doi.org/10.1016/j.cell.2020.01.012).
Their Altai callset, masks and population-specific calling differ from GU's
multi-reference union. The figures therefore provide scale/trend context, not
a claim of exact reproduction or diploid ancestry dosage.
