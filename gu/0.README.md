# gu

古人类片段、ARG/TRACE 与群体遗传分析。同一个 `gu/` 支持 local 和 HPC；与它相邻的 `../0f/` 是共享运行依赖。

## 目录与环境

| 用途 | local 默认值 | HPC 默认值 |
| --- | --- | --- |
| 代码目录 | `/mnt/d/scripts/gu` | `/work/sph-huangj/scripts/gu` |
| 原始数据根目录 | `/mnt/f` | `/work/sph-huangj/data` |
| GU 分析目录 | `/mnt/f/analysis/gu` | `/scratch/DATE/sph-huangj/analysis/gu` |
| GU conda | `/mnt/d/software/anaconda3`，或已安装的 `$HOME/anaconda3` | `/work/sph-huangj/software/gu/conda` |

共享默认值来自 `../0f/0os.sh`，项目设置来自 `f/runtime.env`。命令行可覆盖数据、输出和资源设置。HPC 用 `--date-scratch YYYY-MM-DD` 选择实际日期，恢复已有分析时沿用原日期；`--dir-out` 或 HPC plan 的 `--run-dir` 可明确指定输出。

入口会自动加载 `f/runtime.env`，无需另存一份本机环境模板。若原 `gu-local/` 中另有自己修改过的 `local.runtime.env`，先复制到 `gu/` 并核对路径，再删除旧目录。仓库内的 `gu-local` 没有独有的科学实现；GU 当前使用 `f/shiny/`，旧顶层 `shiny/` 是相同界面的重复布局。

## Local

普通 IBDmix 由同一入口生成 `.cmd`，以本机进程执行。`--jobs-N` 控制同时运行多少个 cohort，`--jobs` 控制一个 cohort 内的并发；二者应根据本机内存合并考虑。显式 `--submit local` 优先于环境中是否存在 `bsub`。

```bash
cd /mnt/d/scripts/gu
bash gu.sh ibdmix --submit local --jobs-N 1 --jobs 1 \
  --chr 22 --grch 37 --target 1kg \
  --dir-target /mnt/f/gen/1kg/37/pfile/chr \
  --dir-out /mnt/f/analysis/gu/1kg --memory-cap 32G

bash arg.sh build --submit local --method threads --format trace \
  --dir-gen /mnt/f/gen/1kg/37 --chr 22 --grch 37 --threads 8 --jobs 1
```

TRACE 使用已通过验证的 ARG：`bash gu.sh trace --submit local --chr '1 2 22' --dir-arg ARG目录 ...`。PhyML 使用原始 COJO lead 表：`bash gu.sh phyml --submit local --loci FILE.jma.cojo --loci-format cojo --grch 37 ...`；其余输入、输出参数见 `gu.sh -h`。

## HPC：普通 IBDmix

普通 IBDmix 可直接在登录节点提交。每个 postfix/cohort 生成独立的 LSF `.cmd`，真正计算在分配的节点内运行。先用 `--run-cmd FALSE` 生成命令查看，再将该参数改为 `TRUE` 正式提交。已经提交的作业应先核查状态，不要重复执行同一提交请求。

`bsub` 无响应时默认等待 300 秒，可用环境变量 `WORKFLOW_BSUB_TIMEOUT_SECONDS` 调整。如果 LSF 明确报告达到等待作业上限，提交器会显示 `[LSF WAIT]`，保留同一个 `bsub` 进程等待名额释放。其他超时记录保存在生成目录的 `submission-*.jsonl`；超时并不表示作业未被接收，应先核对 `bjobs`，再补交未被接收的批次。

```bash
cd /work/sph-huangj/scripts/gu
bash gu.sh ibdmix --submit hpc --date-scratch 2026-11-03 \
  --chr 22 --grch 37 --target 1kg \
  --dir-target /work/sph-huangj/data/gen/1kg/37/pfile/chr \
  --dir-out /scratch/2026-11-03/sph-huangj/analysis/gu/1kg \
  --queue 33 --slots 40 --memory-cap 160G --jobs 1 \
  --jobs-N 8 --run-cmd FALSE
```

生成的 worker 保存已解析的 `DIR_WORK`、`DIR_DATA`、`DIR_SCRATCH`、`DIR_SOFTWARE` 和 GU 项目环境覆盖值，因此以后从另一个 shell 提交同一 `.cmd` 时仍使用相同的数据、软件和 conda 路径。HPC worker 必须有真实 `LSB_JOBID`。

## HPC：ARG、TRACE、PhyML

这些模块使用现成的 `hpc plan` / `hpc submit` 接口。`--submit hpc` 选择路径与执行环境，并不把普通的 `trace`、`phyml` 或 `arg.sh build` 自动改造成调度请求；登录节点上的这些直接计算入口会明确退出。已有分配的 LSF 作业内可继续调用它们。

例如为 ARG → TRACE 建立计划：

```bash
cd /work/sph-huangj/scripts/gu
run_dir=/scratch/2026-11-03/sph-huangj/analysis/gu/1kg/arg-trace-review
bash gu.sh hpc plan arg-trace --submit hpc --date-scratch 2026-11-03 \
  --run-dir "$run_dir" --env-file "$PWD/f/hpc.runtime.env" \
  --target 1kg --grch 37 --chr 1-22,X \
  --dir-target /work/sph-huangj/data/gen/1kg/37/pfile/chr \
  --dir-gen /work/sph-huangj/data/gen/1kg/37 \
  --sample-panel /work/sph-huangj/data/gen/1kg/37/samples.txt \
  --dir-map /work/sph-huangj/data/gen/hm3/37/gmap \
  --queue 33 --threads 4 --memory-gb 96 --walltime 120:00

# 查看生成的 plan.json、jobs/commands.tsv 和 jobs/*.cmd 后提交。
bash gu.sh hpc submit "$run_dir" --submit hpc
bash gu.sh hpc status "$run_dir" --submit hpc
```

| `hpc plan` 方法 | 必需的专用输入与行为 |
| --- | --- |
| `arg` | `--dir-gen`；按染色体构建 ARG |
| `arg-trace` | `--dir-gen`；ARG 完成并验证后合并，再进入 TRACE |
| `trace` | `--dir-arg`；使用已完成、通过验证的 ARG，保持全 cohort 联合推断 |
| `phyml` | `--loci FILE.jma.cojo --archaic-path DIR`；固定 cohort，不进行 IBDmix 式样本分批 |
| `ibdmix` | `--archaic-path DIR`；也可通过这个高级接口按样本批次和染色体安排任务 |

所有方法还需要 `--env-file`、`--dir-target` 和相应的真实文件。启明示例使用 `33` 队列；内存较大的任务应显式选择 `38`、`1t81c`、`2t50c` 或 `v3-6t`，资源不能跨节点拼接。`--rusage-memory-mode` 按集群实际的 per-job/per-slot 设置选择。`gu-hpc.sh` 仍是 `gu.sh hpc` 的入口别名。

失败后先查看 `hpc status` 和日志，再针对明确失败的任务使用 `hpc retry RUN_DIR --indices ...`。计划会校验代码和输入身份；更新代码后为新提交建立新的 run directory，已有分析结果不会被这个补丁移动或删除。

## 帮助与回归测试

```bash
bash arg.sh -h
bash gu-hpc.sh -h
bash gu.sh -h
bash install.sh -h
```

`f/2test/` 保留回归测试或入口自检依赖，不要作为缓存删除。HPC 调度单元测试需要先初始化真实运行配置：

```bash
export submit=hpc
source f/runtime.env
python3 -m unittest discover -s f/2test -p 'test_hpc*.py'
python3 -m unittest discover -s f/2test -p 'test_execution_modes.py'
```

这些测试使用小文件和模拟调度器，不提交真实科学作业；真实集群执行仍需要本机/HPC 已安装的工具和研究数据。

## 启明 GPU 与 PhyML 资源

普通 IBDmix 和 `hpc plan ibdmix` 都支持 `--GPU TRUE`。GPU worker 申请一张卡（`num=1/host`），高级计划的 prepare/merge 阶段仍走 CPU 队列。默认仍为 CPU；仓库的 CUDA caller 是实验实现，先在相同 cohort、染色体、参考、mask、阈值下核对 CPU/GPU 输出，再在站点配置中设置 `GU_IBDMIX_GPU_DEFAULT=TRUE`。显式 `--GPU FALSE` 始终覆盖站点默认。`GU_GPU_MEMORY_GIB` 是主机 RAM，不是显存。

PhyML 的 LSF walltime 与单棵树 timeout 是两个限制。高级计划新增 `--phyml-timeout-seconds 86400` 和 `--phyml-retry-timeouts`，并把它们写入不可变计划。既有计划不能直接改 `plan.json`。已有输出的 TIMEOUT 恢复应在新的 LSF 分配内对原输出执行，设置 `PHYML_TREE_TIMEOUT=86400`、`PHYML_RETRY_TIMEOUTS=TRUE`、`--replace-phyml FALSE`。先检查 `phyml.timeouts.tsv`，不能把流程完成标记解释为每棵树都成功。

高级 PhyML 计划当前仍是一个固定 cohort 的任务；`--max-running` 不会把 COJO leads 自动拆为多个任务。MPI 主要分配 bootstrap replicates，代码保持恰好 100 次 bootstrap；优先按内存实测选择单节点资源，再决定是否按独立 lead 拆分任务。
