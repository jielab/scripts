## Unified local / HPC entry (2026-11-01)

The maintained source is the same in `D:/scripts` and `/work/sph-huangj/scripts`.
Shared platform settings: `../0f/0os.sh`; shared command runner: `../0f/submit_jobs.py`.
Use `submit=local jobs_N=4 ./ENTRY` or `submit=hpc jobs_N=8 ./ENTRY`.
`--submit local|hpc`, `--jobs-N 1..8`, and `--wait TRUE|FALSE` are also accepted.
For metag, `--submit TRUE` submits, `--submit FALSE` only generates; a value is required.
`split` is the public name (classification plus species splitting); the old `classify` command is removed.
`split --queue NAME` sets both pilot and batch queues; it preserves CPU/memory requests.
Large smp metag jobs default to 32 CPU cores: Kraken build uses 32 threads; Kraken split uses 3 workers with 8 threads each plus FASTQ overhead; Kun-Peng-F uses 30 threads plus FASTQ overhead. Smaller jobs retain their lower CPU requests.
The full Kraken profile retains 4 TiB on the smp queue. The spec queue currently has a 168 GB limit.
Selecting a queue never reduces the memory request automatically.
Local .cmd files run in a bounded process pool and wait; failed commands stop new local work.
HPC records real JOBIDs and uses explicit dependencies. Missing bjobs entries never imply success.
GU/LD support `--wait TRUE`; metag retains its stage dependency graph (local stages wait automatically).
`jobs_N` controls local .cmd concurrency and GU/LD HPC concurrency; metag HPC array resources remain in hpc.yml.

### 完整性基线：兼顾现有凭据和持续的快速检查

先在计算节点用已生成计划的绝对 config.json，或者 source f/env.sh 后使用 hpc.yml：

```bash
python3 f/audit_integrity.py --config /absolute/config.json --scope indexes --report
python3 f/audit_integrity.py --config /absolute/config.json --scope indexes --seal /absolute/work/integrity-indexes.json
python3 f/audit_integrity.py --verify-seal /absolute/work/integrity-indexes.json
```

report 只检查凭据结构、文件清单和大小，明确不代表内容校验。seal 会顺序读取选中的文件一次，
校验已有 SHA256，并写入独立基线。该操作可能读取数 TB，应放进 .cmd 作业，不在登录节点运行。
需要覆盖旧 raw、metadata 和已完成 prepared 时，使用 `--scope references`；此范围要求全部
prepared 凭据完整。它也包含当前已经完成的索引。

旧文件没有历史 checksum 时标为 `baseline_only_no_historical_checksum`：
只是确认“从现在起以这些字节为基线”，不能追溯证明以前的 prepared 与 raw 从未变化。
已有索引 SHA256 不匹配时禁止生成基线。修复或确认来源后用新文件名重新审计，工具不覆盖旧基线。

可在实际配置中增加绝对路径：

```yaml
integrity_seal: /absolute/work/integrity-indexes.json
```

随后生成的计划会冻结该基线，提交、worker 启动和成功结束时快速检查文件状态，并绑定本套库的路径与身份。
这不要求每个样本重新 hash 整个索引。普通 stat 检查不能发现所有底层 bit rot；需要时在计算节点运行：

```bash
python3 f/audit_integrity.py --verify-seal /absolute/work/integrity-indexes.json --full
```

尚未建成索引时建立的 references 基线不包含未来的索引。建库/转换完成后必须建立新基线，
再用于 split/compare；代码会拒绝用未覆盖完成索引的基线授权分类。

### 6 TB smp 的资源调优

默认 build、Kraken 和 Kun-Peng-F 仍为 4096 GiB；队列可用 6 TB 不会自动改变 .cmd 的申请。
先检查 `lib_hpc/db/resource_estimate.json`、实际 hash 大小、队列限制和有效 worker 数。
若需要更大预算，可在确认本站允许后测试 5120 GiB，留出系统余量，不能把宣传的 6T 数字直接填满。

大索引在 conservative 预算下可能把 Kraken 从 4 workers 减为 1，但每 worker 仍只有 8 threads。
针对单 worker 测试 16/32/64 threads；多 worker 只有在总内存允许、或已核实共享 mmap 计费后再测试。
Kun-Peng-F 的私有索引不能使用 Kraken 的 shared 内存预算。

sample_batch_size=16 当前仅表示 LSF 作业批次，每个样本仍新起原生分类进程。
官方 Kun-Peng direct 支持一进程输入多组 FASTQ，从而复用一次载入的完整索引；这是后续可实现的优化，
本次修复没有将其伪装成已集成的 production batch。必须额外实现逐样本 ordinal、sample_file.map 校验、
混合 SE/PE 分组、磁盘预算和独立原子发布，验证后再启用。

## 2026-11-01 scheduling defaults

Kraken build: smp, 32 cores/32 threads, 4096 GiB, 168 hours.
Kun-Peng index conversion: short, 40 cores (the queue minimum), 72 hours;
RAM inherits MEMORY_DEFAULT_GIB (currently 160 GiB on HPC, below short's 168 GiB limit).
The conversion remains a sequential hashshard operation; reserving 40 cores does not make it 40-way parallel.
LSF job names omit plan hashes (metag_build, metag_kunpeng_index); immutable
plan directories, JOBIDs and dependency records still identify individual runs.
After code changes, regenerate commands; never submit an old frozen plan.
