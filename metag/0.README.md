# metag

CPU 宏基因组五类并行建库与 FASTQ 分类。入口依次为 `install.sh`（工具、metadata 和参考计划）→ `1.library.sh`（准备、五类建库、发布）→ `2.kraken.sh`（分类与保留原始 FASTQ 的物种拆分）。`3.compare.sh` 是另有完整单库时的 Kraken/Kun-Peng 比较；它不把五类的最终 taxid 拼起来代替联合分类。

启明当前上传数据的验收结果、已补齐的 taxonomy 和逐步提交命令见 [HPC_RUN_20261104.md](HPC_RUN_20261104.md)。

## 统一路径与运行模式

`f/env.sh` **会读取 `../0f/0os.sh`**。启明/local 的根目录、日期和共享参数由该文件维护。`--dir-dat`、`--dir-big`、`--dir-tmp`、`--date-scratch` 通过 `workflow_args` 传入；本项目自己的路径/资源再由 `hpc.yml` 和指定的 profile 决定。

- `submit=hpc` / `submit=local` 选择执行环境；`--submit TRUE` 才实际提交/运行生成的计划，`--submit FALSE` 只生成计划。不要把这两个不同用途的 `submit` 混淆。
- 配置优先级是显式 `--config FILE`（否则 `METAG_HPC_CONFIG`，否则 `hpc.yml`）覆盖 `hpc.yml`。每个 profile 都直接覆盖 `hpc.yml`，**不会继承另一个 profile**；`category_resources` 是整张映射替换，覆盖它时应完整列出需要的类别设置。
- `--root` 改变相对路径和 `{metag_*}` 默认路径的根；配置中已经写死的绝对路径保持原值。
- HPC 的准备并发使用 `prepare_concurrency`，分类数组并发使用 `classify_concurrency`，每节点进程数使用 `classify_workers`。共享的 `jobs_N` 限制 local 数组并发，不是这三个 HPC 参数的替代品。
- 科学计算在 `.cmd` 作业内进行。`--download-metadata` 是显式允许在提交主机下载 metadata；默认不自动下载。

当前启明默认 `DIR_DAT=/work/sph-huangj`、`DIR_BIG=/work/sph-huangj/data`；local 分别为 `/mnt/d`、`/mnt/f`。无需定义 `--dir-tmp`，日期参数不会改变默认路径。

- 原始 FASTQ：`$DIR_BIG/metag/raw`。
- 原始参考：`$DIR_BIG/annot/metag/raw`。
- metadata、库、checkpoint、work 和 split：`$ANALYSIS_ROOT/metag`（启明 `/work/sph-huangj/analysis/metag`；local `/mnt/d/analysis/metag`）。
- 软件：`$DIR_SOFTWARE/metag_parallel`。

`hpc.yml` 默认使用持久目录，`allow_scratch: false`，两个 legacy cache 均为 `null`。路径配置只影响新计划；已有计划/receipt 的迁移与恢复需单独核验。本次代码更新不运行建库或分析。

## 新库：准备、五类并行、发布

初次使用必须提供 taxonomy/assembly metadata。以下二选一，`--metadata-source` 改为真实目录；有 `.cmd` 正在运行时保持同一份代码不变。

```bash
# 已有 metadata：离线生成 setup 计划，不提交。
submit=hpc bash install.sh --config hpc.yml \
    --metadata-source /actual/metadata_source --offline --submit FALSE

# 允许从官方站点下载 metadata，并提交 setup。
submit=hpc bash install.sh --config hpc.yml --download-metadata --submit TRUE
```

第一条只生成计划；审阅后使用日志返回的 `jobs.json` 通过 `metag.sh submit --manifest ...` 提交。setup 成功后再运行：

```bash
submit=hpc bash 1.library.sh --config hpc.yml --submit TRUE
# 如希望建库成功后自动释放已就绪样本的 pilot/split：
# submit=hpc bash 1.library.sh --config hpc.yml \
#     --with-split --dat-list casper --ready-only --submit TRUE
```

准备数组结束后，五类 `microbes/viruses/plants/invertebrates/vertebrates` 独立建库。publish 依赖五个 `done(JOBID)`；任意类别失败或 checkpoint 暂停均不会放行下游。当前起步资源如下，最终仍以每类 `resource_estimate.json` 和真实峰值内存为准：

| 类别 | 队列默认 | 核/线程 | 内存 GiB | 单次时限 |
|---|---|---:|---:|---:|
| viruses | `HPC_CPU_QUEUE`，基线 `33` | 8/8 | 48 | 120 h |
| microbes | `HPC_MEDIUM_QUEUE`，基线 `38` | 32/32 | 448 | 120 h |
| plants | `HPC_HIGHMEM_QUEUE`，基线 `1t81c` | 64/64 | 896 | 120 h |
| invertebrates | 同上 | 64/64 | 896 | 120 h |
| vertebrates | `HPC_HUGEMEM_QUEUE`，基线 `v3-6t` | 64/64 | 1792 | 120 h |

这些请求都是单节点内存；多节点不能直接拼成一个原生哈希表。若估算超过预算，只改相应类别的 `queue` / `memory_gib` / `hours`，重生成计划可保留容量估计和兼容 checkpoint。已经开始构建的类别不要为加速直接改 `threads`：线程数属于该构建的身份，改变后会拒绝复用。

## 原生 checkpoint 与恢复边界

默认 120 小时时限、110 小时软停止、10 小时保存余量，约每 4 小时请求 checkpoint。真正的保存发生在完整输入文件边界，且写出大表需要时间；这里保证的是恢复机制，不能保证全库在 5 天内完成，也不能保证严格每 4 小时落盘。

`CURRENT` 指向已提交的 checkpoint；`progress.json` 可能比持久进度更新。退出码 `75` 代表已暂停且不能当成 DONE。确认同一旧计划的运行作业均已停止后：

```bash
submit=hpc bash metag.sh submit --manifest /actual/plan/jobs.json \
    --retry --cancel-pending
```

只取消该计划记录的待运行依赖，不允许与仍运行的旧作业重叠。生产代码变化会使旧计划身份失效；应先重生成 `.cmd`。保持参考、taxonomy、构建参数/线程和 native binary 不变时，已保存哈希仍可复用。本次新增 query profiles 和修改 README 不修改 native builder 或 classifier。

## 超大 CASPER FASTQ：一个样本一个数组任务

普通默认 `sample_batch_size=8`，每节点一个 worker，会在同一任务依次处理最多八个样本。对单样本 100+ GB 的 CASPER，建议使用新 profile：

```bash
# 库已经 publish 后运行；dataset 名必须等于 METAG_READS_RAW 下的实际子目录。
submit=hpc bash 2.kraken.sh --config profiles/qiming.casper.yml \
    --dat-list casper --ready-only --submit TRUE
```

此 profile 使用启明 `2t50c`（2 TB 节点），申请 32 核、30 分类线程、一个 worker、每任务一个样本、数组最多同时两个任务、120 小时时限、1792 GiB。它不改变参考库参数，也不会触发重建。为节约超大 tar 的额外写入与同盘临时副本，使用 `output_format: directory`，输出到独立的 `{metag_state}/split_casper/kraken`，避免与已有 tar 输出身份冲突。每个物种的 FASTQ 仍为 gzip，原始记录和配对不变。

分类内存由 **五类已发布哈希之和及进程/系统余量** 决定；FASTQ.gz 较大主要增加处理时间和 I/O，不代表必须申请 6 TB。若 1792 GiB 预算不够，使用 `profiles/qiming.casper.6t.yml`，转到 `HPC_HUGEMEM_QUEUE`（基线 `v3-6t`）申请 5120 GiB，其他查询设置和输出目录不变。不要单独覆盖已有 `profiles/qiming.6t-query.yml` 后以为会继承 CASPER 设置；该旧 profile 是每节点 3 workers 的另一套配置。

先观察 pilot 和几个完整样本的 `summary.json`：`classification_seconds`、`split_seconds`、`archive_seconds`、`total_seconds_before_commit`、`artifact_bytes`。一百万 fragments 的 pilot 仅验证运行链路和局部吞吐，不能证明整文件完整，也不能保证超大样本完成时间。只有 CPU、内存和共享存储吞吐都还有余量，才增加 `classify_concurrency`；增加队列节点总数本身不会加速一个 Python 拆分进程。

恢复边界要区分：已完成样本可跳过；完成分类并写入有效 `query.json` 的样本可复用 `taxids.bin`；**单样本分类进行中没有片段级 checkpoint**，分类中断需从该样本开头重做；拆分中断会复用完整分类，但重新做该样本拆分。不要把建库的原生 checkpoint 误解为任意 FASTQ 字节位置都能续跑。

当前 union classifier 和拆分实现是 CPU 路径；申请 GPU 不会让它自动使用 CUDA。保留 CPU 作业。若完整单样本仍超过 120 小时，再单独实现配对一致的分片、全局 ordinal 和合并验收；本次不引入未经验证的 FASTQ 重分片实现。

## local

`profiles/local.yml` 面向 96 GiB 工作站，路径需按本机实际目录检查。local 的五类建库依次执行，数组同时受 `jobs_N` 和配置并发上限限制。

```bash
submit=local jobs_N=2 bash install.sh --config profiles/local.yml \
    --metadata-source /actual/metadata_source --offline --submit TRUE
submit=local jobs_N=2 bash 1.library.sh --config profiles/local.yml --submit TRUE
submit=local jobs_N=2 bash 2.kraken.sh --config profiles/local.yml \
    --dat-list changj --ready-only --submit TRUE
```

完整库的容量估计超过本机预算时会拒绝运行；支持 local 不等于把 TB 级全库强行放进 96 GiB，流程不会自动删减参考来适配。

## 验收

```bash
# 不提交任务；检查入口。
bash 1.library.sh -h
bash 2.kraken.sh -h
submit=hpc bash metag.sh doctor --config hpc.yml

# 调度/恢复/输入完整性定向测试，不接触生产输入。
python3 -m unittest discover -s f/2test -p 'test_parallel_lsf.py'
python3 -m unittest discover -s f/2test -p 'test_entry_runtime.py'
python3 -m unittest discover -s f/2test -p 'test_query_runtime_integrity.py'
```

`doctor` 收集队列、LSF 内存计费和文件系统信息；它不能证明未来资源可立即分配，也不能替代项目 quota 检查。若需实际 native checkpoint 端到端验收，在计算节点生成并运行 selftest 计划：

```bash
submit=hpc bash metag.sh selftest --config hpc.yml --submit TRUE
```

该 selftest 使用很小的合成参考、原生暂停/恢复、五类发布及配对 FASTQ 字节校验；不等同于全量生产运行验收。
